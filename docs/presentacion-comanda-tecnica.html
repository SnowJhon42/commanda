Arquitectura

Monorepo con apps separadas.

COMANDA no esta resuelto como una sola app. El sistema esta dividido por responsabilidades: API, experiencia cliente, operación staff y sitio comercial.

COMANDA_LOCAL/ ├── comanda-backend → API + reglas de negocio + DB ├── comanda-front-client → app cliente mobile-first ├── comanda-front-staff → panel staff desktop-first ├── comanda-website → web pública / comercial ├── docs → runbooks, arquitectura, release, stack └── scripts → arranque, estado, logs, utilidades

Backend

Expone endpoints de autenticación, menú, pedidos, staff, billing, eventos y sesiones de mesa.

Client App

Flujo de mesa, menú, carrito, tracking, pago asistido y feedback final.

Staff App

Login por rol, tableros, salón, QR, feedback, caja, turnos y configuración del local.

Website

Landing pública basada en Next.js para comunicar el producto hacia afuera.

Backend

API en Python con FastAPI.

El backend concentra las reglas de negocio: pedidos, sectores, sesiones de mesa, cobros, eventos, autenticación y validación de transiciones.

fastapi 0.115.8 uvicorn 0.34.0 sqlalchemy 2.0.38 pydantic 2.10.6 psycopg2-binary 2.9.9
  • Routers cargados en `main.py`: `auth`, `menu`, `orders`, `staff`, `admin`, `events`, `table_sessions`, `billing`.
  • CORS configurable con defaults para entorno local.
  • Bootstrap y validación de esquema al startup.

Auth

`python-jose` para JWT y `passlib` con `pbkdf2_sha256` / `bcrypt` para PIN de staff.

Realtime

El sistema usa eventos SSE para propagar cambios de items, pedidos y sesiones de mesa.

Servicios

Hay módulos dedicados a creación de pedidos, routing, estado, impresión, tiempo real, billing, menú e imágenes.

Frontend

Cliente y staff con Next.js 15 + React 18.

Las dos apps comparten stack frontend, pero están separadas por contexto de uso: cliente mobile-first y staff desktop-first.

next 15.5.15 react 18.3.1 react-dom 18.3.1 fetch API EventSource / SSE
Cada frontend consume `NEXT_PUBLIC_API_URL` y se conecta al backend por HTTP y eventos en tiempo real.

comanda-front-client

App cliente con páginas de entrada, menú, checkout, tracking, mesa, mozo y feedback final.

comanda-front-staff

Panel con `AdminBoard`, `Kitchen`, `Bar`, `Waiter`, salón, cierres, resúmenes, QR y configuración del local.

comanda-website

Landing pública en Next.js, separada del flujo operativo interno.

Workspaces

El repo raíz usa workspaces NPM para cliente y staff.

Dominio

Modelo funcional y reglas del sistema.

Concepto Detalle tecnico
Multi-local Desde el diseño se usa `tenant_id` y `store_id` para separar negocio y sucursal.
Sectores `ADMIN`, `KITCHEN`, `BAR`, `WAITER`.
Estados `RECEIVED → IN_PROGRESS → DONE → DELIVERED` con validación de transición.
Modos de servicio `RESTAURANTE` y `BAR`.
Pago Estados `PENDING/CONFIRMED`, split bills, cash requests y sesiones de caja.
Sesión de mesa `table_sessions` + `table_session_clients` para manejar múltiples clientes por mesa.
Feedback `table_session_feedback` guarda rating y comentario al cierre.

Base de datos

Relacional, local en SQLite y online en PostgreSQL.

La fuente oficial local es `comanda_dev.db`. En online hoy la base canónica de `dev` está en Railway Postgres.

  • DB local oficial: `comanda-backend/comanda_dev.db`.
  • DB online de `dev`: Railway Postgres.
  • Legacy conocido: Neon y Render todavía aparecen como drift operativo.

Entidades clave

`stores`, `tables`, `table_sessions`, `products`, `orders`, `order_items`, `bill_splits`, `payment_records`, `cash_sessions`.

Local

SQLite para desarrollo rápido y entorno portable.

Online

PostgreSQL para el backend desplegado y seed demo compartible.

Bootstrap

Scripts de inicialización, seed y bootstrap para Railway Postgres.

Infra y deploy

Separación clara entre local y online.

El proyecto ya documenta una regla operativa estricta: primero local, después GitHub, después deploy y al final smoke test.

Local oficial Backend → http://localhost:8001 Cliente → http://localhost:5173 Staff → http://localhost:5174 Online documentado Backend → https://commanda-production.up.railway.app Cliente → https://comanda-cliente.vercel.app Staff → https://comanda-staff.vercel.app

Railway

Backend desplegado y Railway Postgres como DB canónica de `dev`.

Vercel

Front cliente y front staff desplegados como proyectos separados sobre el mismo repo.

Seguridad mínima recomendada

`JWT_SECRET_KEY` no default, CORS limitado y Basic Auth para la app staff pública.
